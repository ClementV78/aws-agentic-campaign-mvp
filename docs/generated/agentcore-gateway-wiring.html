0Où on en est aujourd'hui

Le moteur métier déterministe (src/urban_campaign_intelligence/) tourne en local et produit déjà des recommandations complètes à partir de data/scenarios.json. Le portage AWS existe sous forme de squelette agentcore-project/UrbanCampaignIntelligencePoc/, généré par l'AgentCore CLI, mais :

Ce qui bloque concrètement aujourd'hui
  • agentcore.json → agentCoreGateways: [] — aucun Gateway ni target n'existe encore
  • aws-targets.json est vide — aucun compte/région configuré, donc deploy.sh refuse de lancer un vrai agentcore deploy
  • app/.../main.py appelle encore le serveur MCP de démo (mcp.exa.ai) et expose l'outil jouet add_numbers, sans lien avec le moteur métier

L'objectif de ce document est de détailler comment combler cet écart : exposer get_weather, get_events, get_mobility, get_zones et get_advertisers via un vrai AgentCore Gateway, et brancher le Runtime dessus.

1Architecture cible

Le Gateway se place entre le Supervisor Agent (l'Agent Strands défini dans main.py, exécuté par l'AgentCore Runtime) et 5 fonctions Lambda — une par tool. Chaque Lambda encapsule un provider déjà écrit dans src/urban_campaign_intelligence/gateway_tools.py (mock, Open-Meteo, Paris Open Data, ou le forecast mobilité). Le Gateway ne fait que router les appels MCP vers ces Lambdas ; il ne contient aucune logique métier. Le scoring déterministe (scoring.py, city_context.py, review.py) reste entièrement côté Runtime, jamais exposé comme tool Gateway.

ComposantRôle

2Déroulé d'une requête

Exemple concret sur le scénario concert_bercy : le Supervisor n'appelle jamais les providers Python directement — il passe systématiquement par le Gateway en MCP. Les agents de contexte (Weather/Events/Mobility) interprètent les données brutes renvoyées par les Lambdas, puis le scoring reste local et déterministe dans le Runtime avant que Bedrock n'intervienne à nouveau pour la review et l'explication finale.

3Plan de câblage, étape par étape

Quatre chantiers séquentiels : d'abord emballer les tools existants en Lambda, puis déclarer le Gateway dans agentcore.json, puis rebrancher main.py dessus, et enfin déployer. Les contrats de tools (tools/gateway_tool_contracts.json) ne changent pas — c'est justement leur rôle : survivre à la transition mock → Gateway sans casser les agents qui les consomment.

4Points de vigilance

Deux prérequis bloquants avant tout déploiement réel
  • Remplir agentcore/aws-targets.json (compte + région) — sans ça agentcore deploy ne part pas
  • Ajouter les 5 AgentCoreGatewayTarget (targetType: "lambda") + la AgentCoreGateway dans agentcore.json, avec authorizerType: "AWS_IAM" pour rester cohérent avec l'endpoint sécurisé visé
Anti-pattern à éviter pendant le portage
  • Ne pas ré-encoder la logique de scoring dans des prompts LLM au passage sur AWS — ARCHITECTURE.md l'appelle explicitement comme le principal risque de régression de portabilité
  • Ne pas transformer un tool Gateway en "agent" : un tool récupère/normalise une donnée brute, il n'interprète rien

Séquence de migration recommandée (issue de ARCHITECTURE.md) : préserver les contrats existants → déplacer les providers derrière des tools Gateway → déplacer les agents LLM vers des modèles Bedrock → déplacer l'orchestration du superviseur vers AgentCore → garder le scoring déterministe hors de la couche LLM à chaque étape.

6Architecture multi-agents cible

La boîte unique "Supervisor Agent" du schéma d'architecture plus haut cache une vraie décision de conception. Le principe retenu : chaque agent n'existe que s'il fait un travail qu'une fonction déterministe ne peut pas structurellement faire — pas de multi-agents pour la forme. Quatre rôles LLM tiennent ce critère, le reste (contexte météo/mobilité, scoring, allocation brute) reste du code déterministe classique.

RôlePourquoi un agent (pas une fonction)Modèle
Advertiser Agent (×N, dynamique)revendication locale par annonceur, justifiée à partir du tool de scoring déterministe (zone × advertiser) — un seul rôle/prompt, instancié en boucle sur get_advertisers(), pas un agent par nom d'annonceur codé en durpetit/moyen
Precedent Agentmatching flou entre le scénario courant et des épisodes passés structurellement différents — une formule à poids fixes ratisse moins large qu'un LLM ici ; doit citer les champs matchés (event_type, zone_ids...) et s'abstenir sous le seuil de confianceléger
Campaign Allocator Agentun seul point d'arbitrage global sur toutes les revendications à la fois — évite qu'une décision locale soit défaite après coup par un contrôle global séparéfort
Review Agentboucle critique bornée (1 retry max) : rejette et renvoie l'allocation à l'Allocator avec un motif, pas une simple validation passivefort/moyen
Ce qui reste volontairement hors agent
  • CityContext Builder et Scoring tool restent des fonctions déterministes (mêmes fichiers que le moteur local : city_context.py, scoring.py)
  • Weather et Mobility restent des tools Gateway — données déjà structurées, aucune interprétation à faire
  • Le comptage d'historique brut (qui a gagné/perdu récemment) reste une requête déterministe sur la Memory, pas un jugement LLM — seul le matching flou entre scénarios justifie un agent

Évolutivité : figer un agent par nom d'annonceur casserait le principe déjà respecté par scoring.py, où _score_advertiser_match(zone, advertiser, city_context) prend n'importe quel dict advertiser en paramètre — aucun nom en dur dans le code. L'Advertiser Agent doit suivre la même règle : un seul rôle générique, instancié dynamiquement une fois par entrée de advertisers.json à l'exécution. Ajouter un 6ᵉ annonceur devient un changement de donnée, pas de code.

Piège d'isolation à ne pas reproduire

Le Supervisor Agent de main.py a déjà une fabrique d'instances par clé : 

def agent_factory():
    cache = OrderedDict()
    def get_or_create_agent(session_id):
        ...
    return get_or_create_agent

Ce cache existe pour garder la continuité d'une session à l'autre — c'est voulu pour le Supervisor. Appliquer le même pattern aux Advertiser Agents serait une erreur : ça ferait fuiter le contexte d'un annonceur vers le suivant dans la boucle (Strands accumule l'historique sur une instance réutilisée), et pire, ferait fuiter le contexte d'un scénario vers le scénario suivant si la clé de cache ne change pas entre deux runs.

  • une instance Agent neuve à chaque annonceur dans la boucle, jamais réutilisée entre deux annonceurs
  • aucun cache par advertiser_id entre deux scénarios — le Graph entier est reconstruit à chaque run
  • pas d'API de "reset" à retenir d'appeler : créer une nouvelle instance est léger en Strands, donc le pattern le plus sûr est de jeter l'instance après usage plutôt que d'essayer de la vider
